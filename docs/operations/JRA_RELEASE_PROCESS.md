# JRA サイト公開方式 — 子連れイベントサイト準拠（移行設計 v1）

正本: `toodataa-ai/tokyo-family-events-ai/docs/RELEASE_PROCESS.md`、同リポジトリの `.github/workflows/deploy.yml`、`.github/production-releases.json`。構成・失敗時の動作を可能な限り揃える。ただし **JRA は発走前に封印した予想・結果・払戻等の証跡が不可逆**なので、これらをさらに強く保護する。

## 1. アプリとデータのブランチ分離

| 役割 | 競馬リポジトリ | 子連れイベントと同等の規則 |
| --- | --- | --- |
| 開発・未承認 UI | `staging/jra-ui-v101-three-plus-ana` → 移行後 `main` | 改修はここで反復。実ユーザーの本番UIを変更しない |
| 承認済みアプリ | `production` | 承認済みのHTML/CSS/JSと表示アルゴリズムの正本 |
| 実行データ候補 | `data-staging` | その時点の `data-production` から開始し、検証後だけ昇格 |
| 実ユーザー用のデータ | `data-production` | 公開済みの予想/結果/台帳を維持。アプリ改修とは別 |
| 公開済みアプリ原本 | `release/*` | **実際の公開検証後だけ**作る。旧版復元候補は公開履歴台帳掲載分だけ |
| 公開済みデータ原本 | `data-release/*` | データ公開成功後だけ作成・追記不可 |
| アプリ公開履歴 | `.github/production-releases.json` | `docs/data/production-releases.json` に読み取り専用で反映 |
| 正式画面版 | v1.00（現行） | v1.01 は承認されるまでステージング扱い。予測モデルのv3.13とは別番号 |

**現在の移行状態:** 既存 JRA Pages は `main/docs` からの自動公開。これは子連れイベントの単一 Pages アーティファクト合成方式とはまだ異なる。現在の利用者向け画面・JRAデータ更新を止めたり、本番 Pages ソース設定を暗黙に切り替えたりしない。UI に関するブランチ初期スナップショットは作成済みだが、Pages ソース切替は別のリリース審査で実施する。

## 2. 現状で実現しているステージング

- ステージング公開先: `https://toodataa-ai.github.io/keiba-notes/staging/`
- 候補の独立ソース: `staging/jra-ui-v101-three-plus-ana`、正式原本は従来の `main/docs`。
- 現時点の互換デプロイは **`docs/staging/**` だけ**を `main` にコピー。 `docs/index.html`、`docs/data/races.json`、`docs/pdfs/**`、`e2e_validation/**` は変更しない。
- HTML へ `noindex,nofollow` をステージング生成時にだけ付加。スマートフォンでも目立ちすぎない右下 9px「STAGING + commit短縮SHA」と2pxの境界マーカー。**正式ソースにマーカーを保存しない。**
- レース一覧等の相対参照は最新の公開データを共有する。固定済み2026/10/12の研究版買い目は `docs/staging/data/three-plus-ana/**` に隔離。
- 固定済み v3.13 の `final_bets`、原本PDF・HTML・proof SHAに改変があれば不合格。穴狙い研究版は正式購入指示ではない。

## 3. 子連れイベントと同じ最終的な公開フロー

1. 普段のアプリ改修は開発ソースにのみ反映、全CIを実行。
2. ステージングを生成する際に **最新 `data-production` の動的レースデータ** を重ねる。途中のUIコミットは本番リリースとは見なさない。
3. JRA全開催場メインについて、主要機能、予想閲覧、PDF、馬場表示、最新プロンプト、結果、地方競馬表示、E2Eなどの非退行をテスト。
4. ユーザー明示承認後に `production` を承認済み開発SHAへ更新する。本番を実際に新画面へ公開し、HTTP/予想データの実体を独立照合する。
5. 公開成功時にのみ `release/YYYY-MM-DD-rN` を不変ブランチとして作り、`.github/production-releases.json` へ version/sha/日付/注記を追加する。失敗した公開は台帳に残さない。
6. 前画面の復元は履歴にあるリリース断面の UI のみ。 `data-production`、出走前原本、過去結果は戻さない。

## 4. 定例・手動の JRA データ更新

アプリ版の承認を待たず、**発走前予想・公式結果・回顧は検証合格後に公開**できるようにする。今後 `data-staging` → `data-production` の経路へ移行する際は以下を守る。

- `data-staging` は毎回現在の `data-production` に合わせて開始し、未公開の失敗候補を持ち越さない。
- 更新対象は実行結果の新規追加／許されたステータス遷移のみ（予想原本・オッズsnapshot・final_bets/proofの改変は禁止）。
- 必要な最低範囲: `docs/data/races.json`、レース別HTML・PDF、決定済み snapshot/proof/evidence、公開manifest、回顧結果。各フォーマット検証後に公開候補を封印する。
- プロンプト、表示ロジック、CSS、JS、ワークフロー変更を通常データ更新に混ぜない。混在したら本番公開を拒否し、ステージング側のアプリ改修へ回す。
- 候補commitと直前 `data-production` SHA を照合し、最新 `production` アプリで再検証。成功時だけ本番データを昇格、アプリ画面は変更しない。
- GitHub Actions成功だけでは完了としない。原本・正本台帳・公開HTTPファイルが一致してはじめて成功。失敗した候補は本番適用せず、現在の公開状態を維持する。
- `JRA/地方 Shadow` の相互ファイル変更禁止およびデータ追記の衝突回避は引き続き必須。

## 5. 公開履歴・ロールバック

- トップページ下部で折りたたみの「公開バージョン履歴」。**実際に公開成功した版だけ**を表示する。
- 現行アプリ版番号と過去版を区別する。データ更新の履歴は別表示する。
- アプリ復元は公開台帳で `release/*` と SHA が一致するものだけを対象とする。
- 競馬結果・予想等データ復元はアプリ復元から分離し、許されたデータスナップショットだけを対象とする。誤った原本上書きは自動化せず fail-closed。
- 任意の未公開 `main` / staging コミットへ直接ロールバックしてはならない。
